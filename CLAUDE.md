# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```
make dev      # npm install (if package.json is newer than node_modules) then `vite` dev server
make build    # npm install (if needed) then `vite build` -> dist/
make preview  # serve the built dist/ locally
make clean    # rm -rf node_modules dist
```

These wrap the plain `npm run dev|build|preview` scripts in `package.json`. There is no lint or test setup in this repo — don't invent one.

To manually exercise the app after a change, start `make dev` and drive it with a real browser (Playwright/headless Chromium works well here); there's no automated test suite to lean on instead.

## Architecture

This is a single-page mind-mapping editor: one React class component (`src/App.jsx`, ~1150 lines) rendering into `src/main.jsx`, styled by `src/styles.css` (design-system tokens/components) + `src/app.css` (page-specific overrides). No router, no other components, no state library — everything lives in `MindMapApp`'s state and methods.

**Origin note:** this app began as a Claude Design "design canvas" prototype (`.dc.html`, a custom template DSL rendered by a `dc-runtime`) and was ported into a plain Vite + React app. The original prototype's `renderVals()` method — which computed a flat object of template values every render — was kept almost verbatim; `render()` just destructures `const v = this.renderVals()` and builds real JSX from it instead of feeding it through the old template compiler. If you're touching rendering, `renderVals()` is where node/edge geometry and styling get computed, `render()` is pure layout of what `renderVals()` produced.

### Data model and layout

- Node tree: `state.nodes` is a flat `{id: {id, text, parent, children[], collapsed}}` map; `state.rootId` points at the root. `buildSeed()` builds this from the literal `SEED` array at the top of the file.
- `layout()` recomputes every node's `{x, y, w, h, depth, sign, vert}` from scratch on every render (no memoization) based on `state.dir` (both-h/right/both-v/down). For a "both" direction, root's children are split into two alternating groups (even/odd index → opposite sides) — inserting a sibling shifts the even/odd parity of everything after it, which can flip later siblings to the other side. This is a known, accepted quirk, not a bug to silently "fix" if you notice it.
- `descendants(nodes, id)` walks the **full** tree regardless of `collapsed` — it does not know about layout. `layout()`'s cross-axis shift step guards every access with `if (pos[d])` specifically because collapsed branches never get a `pos[]` entry; removing that guard reintroduces a crash when collapsing a node.
- Text measurement (`measure()`/`wrapLines()`) uses an offscreen `<canvas>` 2D context (`this.mctx`) with a cache (`this.mcache`, cleared on theme changes) keyed by font-size/weight/text.
- Undo/redo is a plain snapshot stack (`state.past`/`state.future`, JSON string snapshots of `{nodes, rootId, sel}`, capped at 80). Multi-select (below) is deliberately excluded from snapshots — it's ephemeral UI state, not document state — so undo/redo always reset `multiSel` to `[]` alongside restoring `sel`.

### Selection and multi-select

`state.sel` is still always a single, real node id (unchanged invariant — see below); `state.multiSel` is an array of *additional* selected ids, empty for the common single-select case. `selectedIds()` returns the full selection (`sel` first, deduped); `orderedTopLevel(ids)` collapses that down to the ids that aren't themselves a descendant of another id in the set (selecting both a branch and one of its own children should only affect the branch once), in left-to-right document order — every bulk operation below runs on this, not the raw selection.

- **Any plain single-selection action clears `multiSel`.** Arrow-key navigation goes through the `selectOnly(id)` helper for this reason; every other spot that assigns `sel` directly (add/edit/paste/undo/redo/rebuilding the tree from mermaid or a loaded file) sets `multiSel: []` in the same `setState`. If you add a new one, do the same — a stale `multiSel` left over from a previous selection would make the next Delete or drag silently bulk-affect nodes the user no longer sees as selected. (`commitMarquee` is the one place that legitimately assigns a *non-empty* `multiSel` — it too writes `sel` and `multiSel` together in one `setState`, with `sel` = the first caught node in document order.)
- **Ctrl/Cmd+click** (`toggleMultiSelect`, wired in `onNodeDown`) toggles a node into/out of `multiSel`. The root can never join it (it can't be bulk-deleted or bulk-moved, so a mixed selection containing it has no meaning) — toggling it is rejected with a toast. Toggling off the anchor (`sel`) promotes the last `multiSel` entry to be the new anchor if there is one, otherwise it just hides the ring (`selVisible: false`), matching the existing "click empty canvas" convention below rather than snapping `sel` to the root.
- **Ctrl/Cmd+A** (`selectAll`, wired in `mapShortcut`) selects every node except the root — same root exclusion as above, and the reason `removeIds` on the result correctly clears the whole map back down to just the root rather than erroring. Being in `mapShortcut` (not a standalone window listener) means it's naturally already inert while actively editing a node's text or while a plain `<textarea>`/`<input>` (e.g. the sidebar's mermaid source) has focus — those keydown paths never reach `mapShortcut`, so the browser's native "select all text in this field" fires instead, unhijacked.
- **Bulk delete** (`removeSel` → `removeIds`): deletes every `orderedTopLevel` id's subtree in one undo step, then selects a nearby surviving sibling of the first deleted id (or its parent if none survive). `cut()` deliberately does *not* go through this — it calls `removeIds([sel])` directly, because copy/cut/paste stay single-node (one clipboard payload) even with a multi-selection active; only delete and drag-move are multi-select-aware.
- **Pointer model** (changed from the original zoom-centric one): **left-drag on the empty canvas** draws a rubber-band selection box (`onCanvasDown` starts `{kind:"marquee"}`, `onMove` grows it + live-previews hits via `marqueeHits()`, `onUp` → `commitMarquee`). **Left- or right-press on a node** arms a move via `startNodeMove(id, e)`: it selects the node first if it isn't already (so a press-and-drag on a fresh node moves it in one gesture) or keeps the whole selection if the node is part of it, then sets up the same `{kind:"node"}` drag the original left-drag used. The move itself only fires once `onMove` clears the 4px threshold, so a press with no drag is just a plain click/select. **Right- or middle-drag on the canvas**, and **middle-drag on a node**, pan. The **wheel pans** (vertical; `Shift`+wheel horizontal); **`Ctrl`/`Cmd`+wheel zooms** toward the cursor (this is also how a trackpad pinch arrives). `marqueeHits(rect)` takes a canvas-local px rect, converts its corners through `toGraph()`, and returns the visible nodes whose layout box intersects it, in document order — shared by the preview and the commit. `commitMarquee` sets `sel`+`multiSel` from the hits (empty box, or a no-drag click → hides the ring, the "click empty canvas to deselect" convention); `Shift` during the marquee makes it additive (union with the current selection) instead of replacing.
- **Bulk drag-move** (`onNodeDown` → `startNodeMove` / `onMove` / `onUp`): grabbing a node that's already part of the current selection drags the whole `orderedTopLevel` group together (preserving each node's relative on-screen offset via one shared `ghost.dx/dy`); grabbing anything else first collapses to just that node (standard multi-select convention). The dragged set is fixed once at mousedown as `d.moveIds` (further deduped/ordered via `orderedTopLevel`) along with `d.sameParent`; both are used throughout the drag rather than recomputed, since `nodes` doesn't change until drop. **Sibling reordering ("before"/"after") is only offered when every dragged node shares the same original parent** (`d.sameParent`); a mixed-parent group always reparents ("into") instead, since there's no single well-defined sibling slot to insert a cross-branch group into. `onUp` generalizes the old single-node splice logic directly: it detaches/reinserts `d.moveIds` as one contiguous block at the target position, so a multi-node drag with `moveIds.length === 1` behaves byte-for-byte like the old single-select code path.
- Selection ring visibility (`selVisible`) is separate from `sel` itself — `sel` always points at a real node (every editing method assumes this and will throw on `null`), so "click empty canvas to deselect" only toggles whether the ring renders, not the underlying selection (it also clears `multiSel`, unlike hiding the ring via ctrl+click-off above). In `renderVals()`, a node's `<input>` mounts whenever it's in `selSet = selVisible ? {sel, ...multiSel} : {}`, and its ring + z-index bump key off a slightly wider `ringSet ∪ previewSet`: `ringSet` is `selSet` normally but empty while a plain (non-additive) marquee is being dragged — so the box shows exactly what it will select — and `previewSet` is the live `marquee.hits`. This keeps rings, z-index, and input-mounting multi-select- and marquee-aware without touching their per-node logic.

### Theming

`state.theme = {ink, shape, edge, size, invert, svgTransparentBg}`.

- **ink**: `paper|cyan|magenta|yellow|green|purple` each look up a `{solid, text, edge, ring}` quad in the `INK` map (values are `var(--color-*)` refs into `styles.css`). `multi` ("カラフル") is different: each of the root's direct children gets its own color from `MULTI_PALETTE`, inherited by that branch's entire subtree via `branchAncestor()` (walk up to the root's direct child) + `branchColorOf()`. **Branch→color assignment is sticky**, cached on the instance in `this._branchColors`/`this._branchColorSeq` and only ever added to, never recomputed from a branch's current sibling index — an earlier index-based version caused unrelated branches to swap colors whenever a sibling was added/removed/dragged elsewhere. Root itself always resolves to `INK.paper` in multi mode (a node has no branch ancestor).
- **invert**: normally only the root renders as a solid filled "chip" (ink-colored, light text); depth-1 nodes just get colored text on the regular `shape`. Inverting swaps this: depth-1 becomes the chip (in its own ink/branch color) and the root becomes a fixed neutral `INK.paper` anchor. The chip look ignores `shape` entirely for whichever depth has it, same as the root always did.
- **shape**: `box|underline|bare`, decided per-node in the `nodeViews` builder inside `renderVals()`.
- Selection ring visibility (`selVisible`) is separate from `sel` itself — `sel` always points at a real node (every editing method assumes this and will throw on `null`), so "click empty canvas to deselect" only toggles whether the ring renders, not the underlying selection.

### Mermaid sync

`toMermaid()`/`fromMermaid()` only speak the indented `mindmap` dialect (flowchart support was deliberately removed). The sidebar's source textarea always reflects live state (`s.srcDirty ? s.src : this.toMermaid()`) unless the user is actively typing in it, and "反映" round-trips through `fromMermaid()` to rebuild the node tree.

### SVG export

`buildSvg(fontStyle)` does **not** serialize the DOM (nodes are absolutely-positioned `<div>`s, not SVG) — it independently re-derives the same layout/ink/shape/invert decisions as `renderVals()`'s node/edge builders, but resolving every `var(--color-*)` (including `color-mix()` values) to a concrete `rgb()`/`rgba()` string via a hidden probe element (`resolveColor()`), and wrapping text itself with the canvas context (`wrapLines()`) since SVG `<text>` doesn't wrap. If you change how nodes/edges are colored or shaped in `renderVals()`, check whether `buildSvg()` needs the equivalent change — the two are intentionally independent implementations, not shared code.

**Font embedding.** `buildSvg()`'s `<text>` asks for `Source Serif 4, Noto Serif JP, serif`, but a standalone `.svg` has neither web font, so it would fall back to the viewer's generic `serif`. `saveSvg()` (now `async`) first calls `await buildFontStyle(codepoints)` — which fetches `SVG_FONT_CSS_URLS` (the same Google Fonts the app loads), keeps only the `@font-face` subsets whose `unicode-range` covers a glyph actually in the map (plus a `" 0Aa"` Latin seed), fetches each subset's woff2, and inlines them base64 as `@font-face` rules in a `<style><![CDATA[…]]></style>` prepended inside `<svg>`. The base64/CSS never contains `]]>`, so unlike the mermaid metadata it's one CDATA section. Cost: the embedded fonts dominate file size (~0.5 MB for a small all-kanji map, more with vocabulary). If any fetch fails (offline at export time) it falls back to a plain `@import` block (only effective when the `.svg` is later opened online in a browser) and sets `this._svgFontFallback` so the toast says so. The `<style>` sits before `<metadata>`, which doesn't affect `extractMermaidFromSvg()`'s round-trip.

The exported file is round-trippable: `buildSvg()` embeds the same mindmap-dialect text `toMermaid()` produces in a `<metadata id="mindmap-mermaid"><![CDATA[...]]></metadata>` element (any literal `]]>` inside is split across two adjacent CDATA sections, since that sequence can't appear inside one), plus theme/direction as JSON in a second `<metadata id="mindmap-theme">` element (same `{theme, dir}` shape `saveLocal()` bundles into `STORE`) — and `saveSvg()` names the download `<title>.mindmap.svg` to signal that. Dropping a file onto the canvas (`onCanvasDrop` → `loadSvgFile()`) reads it as text; `extractMermaidFromSvg()` pulls the tree back out and goes through the same `fromMermaid()` the sidebar's 反映 button uses (a plain SVG with no such block, or a non-`.svg` file, just gets a "not found" toast instead of loading), while `extractThemeFromSvg()` is best-effort — missing or unparseable JSON (an older export, or a hand-edited file) just keeps the current theme/dir rather than failing the load. `onCanvasDragOver`/`onCanvasDragLeave` only light up the drop outline for a `Files`-type drag (so it doesn't fire during the app's own node drag-and-drop reordering); a window-level `dragover`/`drop` listener pair (added in `componentDidMount`) exists purely to `preventDefault()` a drop that misses the canvas, since the browser's default is to navigate away to the dropped file.

### Persistence — three separate localStorage keys, don't conflate them

- `mm-doc-v1` (`STORE`): the document itself (nodes/rootId/seq + theme/dir as a convenience bundle). Only written/read on the explicit 保存/読み込み buttons (`saveLocal()`/`loadLocal()`) — a user-controlled checkpoint, independent of autosave below.
- `mm-settings-v1` (`SETTINGS_STORE`): UI/theme preferences (theme, dir, sidebarWidth, sidebarOpen). Auto-saved on every relevant change via `componentDidUpdate` (reference/value comparison against `prevState`), auto-loaded in the constructor via `loadSettings()`. Current defaults (when nothing is saved) are ink=`multi`, invert=`true`, svgTransparentBg=`true`, size=`lg`, edge=`curve`, dir=`both-h`.
- `mm-autosave-v1` (`AUTOSAVE_STORE`): a silent, debounced (800ms, via `scheduleAutosave()`) backup of just `{nodes, rootId, seq}`, written whenever `componentDidUpdate` sees any of those three change, and flushed immediately on `beforeunload`/unmount so a closed tab loses at most the in-flight debounce window. Auto-loaded in the constructor via `loadAutosave()` (which validates `nodes[rootId]` exists, falling back to `buildSeed(SEED)` on anything missing/corrupt) — this is what the app opens with on a fresh reload, not the seed, unless nothing has ever been autosaved. A toast ("自動保存から復元しました") fires once on mount when this path was taken. It intentionally does not carry theme/dir (already covered by `SETTINGS_STORE`) and is never touched by the manual 保存/読み込み buttons.
- Boolean settings that default to `true` (`invert`, `svgTransparentBg`) must be read back with an explicit `!== undefined` check, not `||` — `||` would silently stomp an explicitly-saved `false` back to the `true` default on the next load.

### Event wiring gotcha

Per-node callback refs (`n.inputRef`, used to focus+select a node's `<input>` when it starts editing) must **not** be a fresh closure created inline inside `renderVals()`. Because `renderVals()` reruns on every render, a fresh `ref` function every time makes React treat it as a detach+reattach of the DOM node on every keystroke, which re-ran the `.focus()/.select()` and clobbered typed text after 1-2 characters. The fix is `inputRef(id)`, which caches one stable closure per node id (`this._inputRefs`) — keep using that pattern for any future per-node ref callback.
